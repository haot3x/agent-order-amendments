# ERC-8427 funding integration experiment

This local test connects the experimental ERC-8001 order-amendment profile to the registered-grant revision of ERC-8427. It uses the upstream registry and direct executor, not a mock budget counter. It is our own integration fixture, not an independent implementation, upstream endorsement, or a new ERC.

## Reproduce

```sh
npm ci --ignore-scripts
npm run test:spend-grants
```

The 10 integration tests passed locally on 14 October 2026. They start and stop a disposable Anvil chain on localhost, with synthetic tokens and public development accounts. No public-chain RPC, wallet, real funds, or Finch backend is used.

The five upstream CC0-1.0 files are pinned unchanged at `tankcdr/erc-spend-grants` commit `d70b04cd3f72ea57882a1afd6c6514a02f96e1b1`. [The manifest](contracts/vendor/erc8427/manifest.json) records SHA-256 checksums, which the integration compiler checks before compiling them with pinned solc 0.8.28. Our order contract and fixture use solc 0.8.37. Both target Cancun with via-IR and optimizer 200; the deployed contracts interact across the ABI boundary.

## Funding boundary

`SpendGrantOrderFixture` extends the order experiment's internal funding hook. The existing order code still checks exact buyer and escrow balance deltas and controls the isolated application call. Its signed message format, domain, bilateral acceptance, order revision and consumed-on-failure semantics are unchanged.

The fixture has one immutable principal, registry and executor. The principal registers a grant whose delegate and fixed recipient are the order fixture, then binds that grant once. Its orders share that grant. The buyer approves only the upstream executor; the order fixture has no direct token allowance.

The fixture cannot forward arbitrary calls or submit detached spend authorizations. It calls the executor with the bound grant, the order's fixed token, the amount derived by the order code, and itself as escrow recipient. Another caller cannot choose a different buyer, recipient or funding grant. The fixture also funds initial offers through the same grant.

For an amendment, the call chain is:

```text
Ready coordination
  -> isolated order application call
     -> validate current order and agreed terms
     -> upstream executor.spend(grantId, token, supplement, order escrow)
        -> registry.consume against current grant terms and usage
        -> token transfer from principal to escrow
     -> verify exact balance deltas
     -> update escrow, terms, revision and amendment nonce
```

If any application step fails, its grant debit, token movement, order writes and logs roll back together. The outer coordinator still records `Executed, success=false`. Restoring spending capacity does not revive that coordination: a new intent and fresh acceptances from both parties are required.

## Results

Setup uses a grant with lifetime cap 1000, funding an earlier order for 600 and the target order for 100. Lifetime usage is therefore 700 and the target is active at revision 0. The setup debits are allowed to leave a 60-second rolling window before testing, isolating the lifetime cap. Cap updates keep `maxPerCall <= maxPerWindow <= maxTotal` valid. Both parties consent to increasing the target order's total price from 100 to 180.

| Case | Observed result |
| --- | --- |
| Cap lowered to 800 before execution | Supplement 80 succeeds; usage 780, target escrow 180, revision 1; the other order is unchanged. |
| Preflight passes, then cap lowered to 750 | `OVER_CUMULATIVE_CAP` (10); usage stays 700, target escrow 100, revision 0; no debit or transfer logs persist. The earlier cap update remains effective. |
| Capacity restored after failed application | Old coordination remains terminal; a fresh intent with only one acceptance cannot execute; old acceptance cannot be reused; both new acceptances permit one supplement. |
| Grant revoked after consent | `REVOKED` (5); no funding or order changes. |
| Token transfers then returns false | Executor failure rolls back the upstream debit, token movement and order state. |
| Token returns success but delivers one unit less | The order's `RECEIVED_AMOUNT` check rolls back even the already returned executor call and its grant debit. |
| Two accepted orders compete for 100 remaining | First supplement 80 succeeds; the second 80 fails using current usage, without changing either order further. |
| Outsider knows grant ID or tries another buyer | Direct executor spend, use of another buyer's funding, and unauthorized/repeated grant binding are rejected. |
| Token callback reenters execution | Reentrancy is rejected; one supplement and one revision increment persist. |
| Agreed scope change has zero supplement after revocation | The order change succeeds without a grant debit; revocation governs future spending, not the underlying service agreement. |

The test source is [test/spend-grants-evm.test.mjs](test/spend-grants-evm.test.mjs).

## Limits

- `check` is a preflight read, not a budget reservation, signature check, or guarantee of token transfer. Execution always consults current grant state.
- Grant version and order revision are distinct. `update(expectedVersion, ...)` guards grant updates; it does not provide order-party consent.
- This fixture shares one grant across its orders. Several independent grants do not form one aggregate agent budget.
- Grant usage counts gross transfers into escrow. An order refund does not restore grant usage; provider payout does not debit the grant again. Net-budget refunds need a separate policy.
- This exercises the direct contract-delegate path only. It does not exercise ERC-7710, native currency, relayed delegate signatures, Arc deployments, or the complete upstream test suite.
- The underlying profile still lacks review timeouts, disputed-delivery resolution and audited production security. This test does not establish an independent adopter or full ERC conformance.
